# 架构与维护边界

D2RHub 的底座是 Windows 上的多账号运行。识别统计、跟房、悬浮窗与桌宠是按需加载的完整功能，重要程度由用户的工作流决定。

## 领域对象

| 对象 | 身份与边界 | 持久化与生命周期 |
| --- | --- | --- |
| 游戏安装 | 国服 CN / 国际服 Global；亚美欧共享国际服安装 | 路径配置属于安装，账号选择安装与区域 |
| 账号 | 稳定账号 ID | 认证、游戏设置与运行状态隔离；启动由队列和账号租约控制 |
| 游戏 Mod | 游戏安装 + Mod 文件夹名 | 文件操作受统一互斥保护；引用检查不能只比较完整启动参数 |
| 启动预设 | 某个游戏版本的一组参数 | 账号和启动方案引用；编辑仅影响同一游戏版本 |
| Hub 扩展 | 内置能力 ID | 添加使设置入口可用，启用决定运行服务；移除停止服务并保留配置 |
| 下载资源 | 资源 ID + 独立版本 + 校验信息 | 成品 Mod 与独立加工器不随主程序版本隐式改变 |

`installed_optional_modules` 是历史配置字段，表示 Hub 中添加的内置功能，不是插件市场中的二进制安装。兼容字段可以保留，界面用“扩展”“添加”“移除”描述。

## 前端

- `components/`：可复用 UI、主界面组合与应用壳。
- `features/`：按功能组织界面、控制器与纯模型。Settings 负责编辑入口；Mod、任务、能力、自动跟房各自有领域模块。
- `store/`：后端已提交的配置、账号和运行快照。设置中的未提交输入不应覆盖这里的持久状态。
- `platform/tauri/`：统一的命令、事件与错误边界。UI 不应该散落原始 IPC 调用协议。
- `styles/`：主题、颜色、排版等共享基础；功能布局样式与对应功能放在一起。

设置导航使用稳定 tab ID，按“游戏 / 扩展 / 应用”展示。已添加扩展有直接入口。Mod 管理的“已安装 / 下载与更新”共用当前游戏版本；单条 Mod 自己持有展开状态和参数草稿，不持有共享目录数据。

识别页只负责账号、Mod 选择、运行识别与记录偏好。账号与运行准备保持可见，记录筛选和诊断按需展开。识别目标独立选择，不会在开启时被自动跟房的主号偷偷替换。

| 模块 | 责任 |
| --- | --- |
| `features/mods/featureContract.ts` | Mod 功能 ID、选择规则、加工结果与命令参数 |
| `features/mods/workflow/` | 加工来源、目标账号、配方、检查、执行、取消及返回原入口 |
| `features/modResources/` | 资源读取、安装状态、任务恢复、错误与目录版本隔离 |
| `features/settings/globalSettingsSession.ts` | 独立编辑草稿、变更字段合并与提交版本 |
| `features/settings/panels/` | 设置面板组合，不持有重复的加工执行逻辑 |

Mod 加工只维护一份表单和工作流。入口明确携带目标账号及来源；请求的账号失效时提示重新选择，不擅自换成第一个账号。只读检查不会导航或修改配方。加工完成但应用账号失败时保留生成结果，重试只应用结果。安装任务按资源和游戏版本显示进度，离开后可以恢复失败或取消状态。

## 后端

```text
commands          IPC 入参、应用调用、结果与事件
    ↓
application       用例、配置事务、运行协调、权限与互斥
    ↓
领域逻辑与模型     Mod 身份/引用、功能组、账号与启动方案
    ↓
基础设施          文件、Windows 进程与注册表、音频、网络、数据库
```

| 模块 | 责任 |
| --- | --- |
| `domain/mod_processing.rs` | 功能身份、配方、指纹和旧协议兼容；不读取文件或调用 Tauri |
| `domain/mod_arguments.rs` | Mod 名称、启动参数解析与保留无关参数的变换 |
| `domain/mod_catalog.rs` | 目录身份、引用、持久结构和纯变更计划 |
| `audio_mod.rs` | 账号加工用例与对外命令，协调检查、执行和应用 |
| `audio_mod/validation/` | 清单身份、布局、内容完整性与来源验证 |
| `audio_mod/generator.rs`、`filesystem.rs` | 加工器调用、受限目录与文件访问 |
| `audio_mod/replacement.rs`、`modification.rs` | 替换日志、备份恢复与可逆功能修改 |
| `mod_catalog/transactions.rs` | 目录、边车记录、账号引用的事务与恢复 |
| `infrastructure/managed_process.rs` | 有超时、取消、输出上限和退出回收的子进程生命周期 |

主用例仍保留在对应功能根模块，避免一次改动同时改变 IPC、持久格式和游戏协议。领域规则不依赖运行服务；基础设施返回数据，由用例决定后续动作。

应保留的现有可靠性边界：

- `application/configuration.rs`：配置提交顺序与运行能力协调。
- `application/capability.rs`、`task_runtime`：能力生命周期、任务进度与失败反馈。
- `durable_fs`、模块配置事务：原子写入、恢复与回滚。
- `application/multi_instance`：账号租约、可信启动上下文与队列。
- `application/mod_mutation.rs`：加工、资源安装、删除、功能开关、恢复、游戏启动与重启之间的统一互斥。

## 变更规则

1. UI 不能根据“开关为真”宣称后台服务运行；运行状态来自后端观测。
2. 保存只提交用户改变的字段。后台事件更新未编辑字段；保存失败保留可重试草稿。
3. Mod 文件变更先取得统一操作租约，再检查运行进程、引用和目录状态。游戏启动批次持有同一租约直到运行进程登记完成；新命令也必须加入这一边界。
4. 文件夹引用按物理 mods 目录和不区分大小写的 Mod 名称判断；国服/国际服路径可能是同一安装的别名，参数顺序、附加标志和路径别名都不能绕过引用保护。
5. 资源初次读取和自动轮询只检查元数据；用户主动检查更新或执行安装时校验受管目录内容，安装前再次核对。已修改、已加工、来源不明或安装记录损坏的内容不覆盖。无安装记录的旧版成品需与下载包比较后才能接管。
6. 一个动作只维护一个生产实现。开发预览复用真实组件，通过隔离 fixture 提供数据。
7. 加工器异常、超时或取消后，先终止并回收子进程再释放 Mod 操作租约。持续输出不能阻止取消；错误输出有内存上限。
8. 发布准备对独立源码快照运行检查，保存源码身份和检查证据后才构建；补传复用已验证字节，不重新构建。
9. Tauri 自动权限文件以当前命令清单为准。构建只淘汰完整匹配生成模板的过时文件，保留自定义权限，避免旧工作区污染 schema。

继续维护时按用例与状态生命周期拆分，不以文件长度作为唯一标准。现有协议、恢复日志、账号兼容与启动保护是重构约束；新增能力应使用以上边界，并为行为变化提供回归验证。
