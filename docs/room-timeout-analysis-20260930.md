## 原因判断与证据边界

最符合“此前多次可派发、连续两次失败、随后恢复”的解释是某个 D2R 窗口在切换场景或忙碌时未及时处理同步消息，触发 250ms 等待上限；这是推断，尚未证明。窗口销毁、线程退出或其他投递失败也可能返回零。微软文档说明该 API 返回零同时覆盖失败和超时，且不保证每次失败都设置 LastError，必须先清零再读取：[SendMessageTimeoutW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendmessagetimeoutw)。

日志中的工作集整理发生在 00:05:47 和 00:05:53，距失败约 18 分钟，不能作为直接原因。也没有证据证明 HUD 定时器或补发回车造成这两次失败；本次对这两项的修改来自用户明确要求，不能视为超时问题已修复。

“指令已全部派发”只证明发送流程完成，不证明游戏已成功建房或所有小号已入房。诊断包没有游戏状态确认，不能据此判断实际跟房成功率。

## 建议方案（本次未实施）

1. **先补齐诊断**：每条消息记录 task、账号角色、PID、HWND、子步骤、虚拟键、down/up、发送策略、耗时；调用前 SetLastError(0)，失败后记录 GetLastError。保持房名、密码等内容脱敏。区分超时、窗口变化、权限/一般错误。
2. **做可对照的复现**：确认所有窗口已结束加载，再触发一次；记录前后台、帧率、场景和失败账号。可通过现有设置比较同步/异步按键策略，比较的是实际表单和入房结果；异步入队成功也不是执行成功。本次未改用户设置。
3. **若确认是忙碌超时**：评估将单条消息上限从 250ms 调整为有上限的更宽等待（例如 1000ms，作为实验值），保留任务总预算、取消和进程身份验证。原有“表单等待”或“小号进房间隔”不能改变 SendMessageTimeout 的硬编码上限。
4. **避免盲目重放**：超时不证明按键未被执行。尤其 Enter 和 Esc 不应自动重试整串；失败后终止流程、释放修饰键并重新确认页面状态，再决定重开表单。必要时单独设计安全的 key-up 清理。
5. **长期区分投递与业务确认**：分别展示“指令派发完毕”和“确认已入房”，引入可靠的游戏状态反馈后再做建房/跟房重试。

验收应包含：忙碌窗口、失效窗口、取消、按下成功但释放超时、不重复提交、修饰键最终释放，以及正常场景时序不退化。
